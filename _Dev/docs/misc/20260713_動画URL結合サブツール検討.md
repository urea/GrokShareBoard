# 動画URL結合サブツール検討 (2026/07/13)

> **2026/07/13 方針更新**: 処理サーバーと一時ストレージを追加する案は採用しない。GrokShareBoard 配下の静的ページ `/tools/video-join` で、利用者が Grok から保存した MP4 を選択し、FFmpeg WebAssembly により利用者ブラウザ内だけで結合する方式を採用した。以下の専用バックエンド案は比較検討の記録として残す。実装結果は [20260713_動画結合ブラウザツール実装.md](./20260713_%E5%8B%95%E7%94%BB%E7%B5%90%E5%90%88%E3%83%96%E3%83%A9%E3%82%A6%E3%82%B6%E3%83%84%E3%83%BC%E3%83%AB%E5%AE%9F%E8%A3%85.md) を参照する。

## 結論

複数の Grok Imagine 動画を順番に単純結合し、完成 MP4 を利用者へ返す機能は、**Grok Share Board 配下の独立したサブツールページとして提供する**。

- 本体は「Grok の作品・プロンプトを共有、閲覧、検索する掲示板」であり、動画編集ジョブを抱える責務とは異なる。
- 現在の GitHub Pages を中心とする静的構成を維持し、FFmpeg WebAssembly を使って利用者ブラウザ内で処理する。
- 完成動画、元動画、Grok URL をサイトの投稿や DB に保存せず、利用者端末の外へ送信しない。

名称は **「Grok Video Join / Grok動画結合」** とする。初期版の出口は **MP4 ダウンロードのみ** とし、X 投稿は対象外とする。

## 想定する利用例

利用者が、公開済みの Grok Imagine 投稿 URL を複数入力する。

```text
https://grok.com/imagine/post/62a88f30-9898-4ee7-9e50-f8b068867b56
https://grok.com/imagine/post/40dc55bf-f1f7-4339-ab1a-50ed1e74e82a
```

ツールは入力順で動画を検証し、`1 → 2 → ...` の一つの MP4 として返す。トリミング、字幕、BGM、速度変更、トランジションは初期版の対象外とする。「単純に繋ぐ」用途に絞る。

> 上記 2 URL は入力例として扱う。今回の調査環境から各投稿ページの動画実体・公開状態までは確認できなかったため、実装時には実際に公開済みの動画かを結合前に検証する。

## 利用者フロー

1. Grok で各動画を **シェア** または **X に投稿** して外部から取得できる公開状態にする。
2. 「動画URL結合」ページに Grok 投稿 URL を改行区切りで入力する。
3. ツールが URL ごとに「動画として取得できるか」「上限内か」を検証し、サムネイル・秒数・並び順を表示する。
4. 利用者が順序を並べ替え、「結合してダウンロード」を実行する。
5. 一時ジョブで結合し、完成 MP4 を一度だけダウンロードさせる。
6. ダウンロード完了または有効期限切れ後、入力動画と完成動画を削除する。

取得できない URL は、公開化して再試行する案内を出す。Grok 側で動画の外部取得が許可されない場合は、利用者が元動画を端末へダウンロードしてからアップロードする代替導線を用意する。

## 保存方針

「当サイトに動画を保管しない」は、次のように明文化する。

| 対象 | 方針 |
| --- | --- |
| 入力した Grok 投稿 URL | 結合ジョブ完了後に削除。投稿一覧・検索 DB には保存しない。 |
| 取得した元動画 | 結合処理中だけの一時ファイル。保存領域はジョブ専用で、完了・失敗・タイムアウト時に削除。 |
| 結合後 MP4 | ダウンロード用に短時間だけ保持し、その後自動削除。恒久公開 URL を作らない。 |
| ジョブ記録 | 監視に必要な最小限（作成時刻、件数、容量、成否、エラー分類）のみ。元 URL、動画、プロンプトは記録しない。 |

完全な「ゼロ保存」は、サーバーで複数の動画を結合する以上は現実的ではない。FFmpeg は入力を読み込み、出力を組み立てる一時領域を必要とするためである。正確な約束は **「恒久保存しない。処理用の一時保存だけを、短い TTL で自動削除する」** とする。

## なぜ本体に実装しないか

| 観点 | 本体（Grok Share Board） | 動画結合サブツール |
| --- | --- | --- |
| 主目的 | 公開作品とプロンプトの閲覧・検索 | 個人利用の一時的な動画加工 |
| データ | 投稿 URL、メタデータ、プロンプト | 一時ファイルと短命なジョブ状態 |
| 実行環境 | GitHub Pages を含む静的配信 | FFmpeg を実行できるバックエンド |
| リスク | 公開コンテンツの表示 | 大容量転送、処理時間、悪用対策 |
| UI | 投稿フォーム・一覧・詳細 | URL リスト、順序編集、進捗、ダウンロード |

ヘッダー等から「ツール / Tools」として遷移させてもよいが、ルート・デプロイ・監視・利用上限は分離する。これにより、結合機能の負荷や障害が掲示板の閲覧・検索を巻き込まない。

## 実現方式の比較

### A. ブラウザだけで結合

`ffmpeg.wasm` 等を使い、利用者のブラウザ内で結合する案。

- 長所: サーバーへの動画保存が不要。
- 問題: Grok CDN の CORS、認証、URL 変更でブラウザが動画本体を読めない可能性が高い。長い動画では端末メモリ・処理時間も大きい。
- 判定: **URL 直接入力を主機能にする方式としては不採用**。端末にダウンロード済みの MP4 を選ぶ「ローカル結合モード」なら将来の選択肢。

### B. 専用バックエンドで一時取得・FFmpeg 結合（推奨）

URL をサーバー側で検証・取得し、短命なワーカーで FFmpeg を動かす案。

- 長所: 利用者は URL を並べるだけでよい。形式の検査、再エンコード、容量制限を一元化できる。
- 注意: 静的 GitHub Pages 単体では稼働できない。コンテナまたは長時間ジョブ対応の実行環境と、TTL 付き一時オブジェクト保存が必要。
- 判定: **初期版の本命**。

### C. 外部動画編集 SaaS へ転送

- 長所: 自前の実行基盤を持たずに済む。
- 問題: 利用者の Grok URL・動画を第三者へ渡すことになり、料金、規約変更、プライバシー、成人向けコンテンツ可否に依存する。
- 判定: 対象サービスの規約と費用を個別確認できるまで保留。

## 推奨アーキテクチャ

```text
利用者ブラウザ
  └─ URLリスト送信
       ↓
結合API（URL検証・上限判定・ジョブ発行）
       ↓
一時ワーカー（Grok公開動画を取得 → ffprobe → FFmpeg concat）
       ↓
TTL付き一時オブジェクト領域
       ↓
署名付き一回限りダウンロードURL → 利用者
```

- **API**: 許可する URL は初期版では `https://grok.com/imagine/post/<UUID>` に限定する。リダイレクト先、プライベート IP、任意ホストへのアクセスを拒否し、SSRF を防ぐ。
- **動画解決**: Grok 投稿 URL から動画実体を取得できるかを、ジョブ前にサーバー側で確認する。取得不可なら結合を始めず、公開化またはローカルファイル方式を案内する。
- **検査**: `ffprobe` で動画・音声ストリーム、解像度、FPS、コーデック、尺、容量を確認する。
- **結合**: 形式がそろう場合だけ `concat demuxer` + stream copy を試し、そろわない場合は H.264/AAC・固定解像度/FPS に再エンコードして結合する。初期版では互換性を優先し、必要なら常に再エンコードする。
- **配布**: アプリ本体の公開ディレクトリには置かず、署名付き URL で直接ダウンロードさせる。TTL は例として 15〜60 分とする。
- **削除**: `finally` 相当でワーカーの一時ファイルを削除し、オブジェクト領域にも TTL ルールを設定する。ジョブが異常終了した場合にも残らないことを監視する。

## 初期版の制限・安全策

| 項目 | 初期値の案 |
| --- | --- |
| 入力件数 | 2〜10 本 |
| 1本あたりの長さ | 30 秒以下（要実測調整） |
| 合計時間 | 3 分以下 |
| 合計入力容量 | 例: 250 MB 以下 |
| 出力形式 | MP4（H.264 video + AAC audio） |
| 利用頻度 | IP または匿名トークン単位でレート制限 |
| 認証 | 初期版は不要。ただし濫用時はログインまたは招待制を検討 |
| 失敗時 | 元 URL・動画本体を画面やログへ露出せず、エラー種別と対処だけを示す |

外部 URL を取得するため、SSRF 対策、最大ダウンロードサイズ、接続・総処理タイムアウト、リダイレクト回数制限、コンテンツタイプ検査は必須とする。FFmpeg は独立ワーカーで実行し、CPU・メモリ・ディスク使用量を上限化する。

## X 投稿について

「ダウンロードか Twitter 投稿をしてもらう」という出口は、初期版では **ダウンロードを標準** にする。

- X への自動投稿には、利用者ごとの認可、投稿権限、動画アップロード API、失敗時の再送、利用規約・料金の確認が必要になる。
- サービスが利用者の X アカウントや完成動画を扱う範囲が大きくなり、単純結合ツールの初期目的から外れる。
- 初期版では「ダウンロード後に X へ投稿」の案内・共有ボタンにとどめる。

自動投稿を後から追加する場合も、完成動画の一時保持期限内に、利用者が明示的に X 連携・投稿内容・公開範囲を確認する方式とする。利用者の代わりに自動投稿したり、URL 入力だけで投稿したりはしない。

## UI の最小構成

- 独立ページのタイトル: `Grok Video Join / Grok動画結合`
- 説明: 「公開済みの Grok 動画 URL を入力順に、ひとつの MP4 に結合します。動画はダウンロード後に自動削除されます。」
- URL 入力欄: 改行区切り、追加・削除、ドラッグで並べ替え
- 検証結果: 各 URL の取得可否、サムネイル、尺、並び順、エラー案内
- 実行部: 合計尺・推定出力サイズ・保存期限を表示し、`結合してダウンロード` ボタン
- 完了部: ダウンロードボタン、失効時刻、手動削除ボタン
- 代替導線: 「Grok 側でシェア / X 投稿して再試行」「元動画を端末へ保存してローカル結合モードを使う」

## 実装前に確定すべきこと

1. 1 日あたりの想定件数と、許容する 1 ジョブの最大尺・容量。
2. 成人向けコンテンツを含む可能性を前提にした実行基盤・一時ストレージの利用規約適合性。
3. Grok 公開済み投稿から、サーバー側で動画本体を取得できる実測結果。今回の 2 URL を含め、公開状態の異なるサンプルで確認する。
4. 一時ファイルを TTL 後に確実に削除できること、および異常終了時の掃除をテストできること。
5. 初期版を URL 専用にするか、取得失敗時のローカル MP4 アップロードを同時に出すか。

## 推奨する次の一手

実装に入る前に、専用の小さな検証環境で次を行う。

1. 公開済み Grok URL 2〜3 本から動画実体を安全に取得できるか確認する。
2. 同一形式・異形式の動画を FFmpeg で結合し、出力 MP4 の再生を確認する。
3. 上限（本数、尺、容量）を超える入力、非公開 URL、画像 URL、リダイレクト URL を拒否できるか確認する。
4. 完了・失敗・タイムアウトのすべてで一時ファイルが削除されることを確認する。

この検証で「Grok URL のサーバー取得が不安定または規約上扱えない」と判明した場合は、URL直接結合を撤回し、**利用者が先に端末へダウンロードした MP4 をローカルで結合するツール**へ切り替える。
